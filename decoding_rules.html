바이트 하나하나가
어떻게 뜻이 되는가

.dd 파일은 Type–Name–SubType–Value 로 이어지는 이진 TLV 스트림입니다. 매직에서 시작해 트레일러 체크섬으로 끝나는 이 흐름을, 실제 바이트를 한 칸씩 짚어가며 디코더가 읽는 순서 그대로 풀어봅니다.

① 전체 레이아웃 ② 형식 감지 ③ 필드 구조 ④ 타입 태그표 ⑤ 예제 한 칸씩 ⑥ 까다로운 규칙 ⑦ 체크섬 ⑧ 텍스트 형식
01

먼저 큰 그림 — 파일 한 개의 뼈대

.tdf 는 사실 ZIP 아카이브이고, 그 안에 여러 개의 .dd 가 들어 있습니다. .dd 하나는 항상 이 네 덩어리로 되어 있습니다 — 위에서 아래로 순서대로 읽습니다.

MAGIC · 4B
17 FA AE 4E — "나는 바이너리 .dd 다" 라는 시작 표식
STRUCT · 0x0B
최상위 구조체를 연다. 이 안에 모든 필드가 중첩되어 담긴다.
…필드들…
Type–Name–SubType–Value 필드가 반복 (③에서 자세히)
END · 0x00
최상위 구조체를 닫는다. 열린 컨테이너는 반드시 END 로 닫힘.
TRAILER · 4B
본문 전체의 체크섬 (예: BC 94 26 A8). 구조가 아니라 무결성 검사용 (⑦).

핵심 감각: 앞 4바이트는 매직, 뒤 4바이트는 체크섬. 그 사이가 실제 데이터 구조입니다. 파싱할 때 맨 끝 4바이트는 떼어 놓고 시작합니다.

02

이게 바이너리야, 텍스트야? — 형식 감지

.dd 는 두 가지 형식이 섞여 존재합니다. 디코더는 파일을 열자마자 이 3단계 규칙(detect_format())으로 어느 쪽인지 먼저 판정합니다 — 위에서부터 순서대로, 걸리는 즉시 확정.

Q1 앞 4바이트가 매직 17 FA AE 4E 인가? → 바이너리
▼ 아니면
Q2 NUL(0x00) 바이트가 있고 & 출력가능문자 비율 < 85% 인가? → 바이너리
▼ 아니면
Q3 그 외 전부 — 사람이 읽는 중첩 텍스트 → 텍스트

Q2 가 있는 이유: 매직이 없는 변형 바이너리도 놓치지 않으려는 안전망입니다. 이진 데이터는 NUL 이 흔하고 출력 불가능한 바이트가 많다는 성질을 이용합니다.

03

필드 하나의 구조 — TLV 네 조각

바이너리 본문은 필드의 반복입니다. 이름 있는 필드 하나는 언제나 이 네 조각 순서를 지킵니다.

09Type
6E 61 6D 65 … 00Name (NUL종료)
08SubType
3F D0 00 00 …Value

Type = 0x09 (STRING)

"여기서 이름 있는 필드가 시작된다"는 신호. 이름 필드는 항상 0x09 로 시작합니다. 바로 뒤엔 필드 이름이 옵니다.

Name = ASCII + 0x00

필드 이름. NUL 바이트(0x00)로 끝납니다. 예: lens_magnification\0.

SubType = 값의 타입

값이 무슨 타입인지 알려주는 1바이트 태그. 0x08 이면 float64, 0x0B 이면 중첩 struct… (전체표는 ④).

Value = 실제 값

SubType 에 따라 길이가 정해집니다. 스칼라(고정폭)·문자열(NUL종료)·컨테이너(END로 닫힘) 중 하나.

컨테이너인 ARRAY(0x0A) 와 STRUCT(0x0B) 는 값 자리에 자식 필드들을 담고, 마지막에 END(0x00) 로 닫힙니다. 그래서 구조가 얼마든지 깊게 중첩될 수 있습니다.

04

타입 태그표 — 1바이트가 값의 성격을 결정

SubType(그리고 배열 원소의 태그)에 오는 1바이트가 값의 종류와 폭을 정합니다. 모든 다바이트 수치는 big-endian 입니다.

END/종료 수치 문자열 컨테이너
태그이름범주크기값 인코딩 / 실측 메모
0x00END종료—컨테이너(struct/array) 닫기
0x01INT8_A수치1B부호있는 8비트. 이름 필드에선 미관측 (희소)
0x02INT8_B수치0~1B0 전용 마커로 관측 — 이름필드 602/602 이 0
0x03UINT8수치0~1B0 전용 마커로 관측 — 이름필드 50/50 이 0
0x04INT8_C수치1B실제 int8 값 캐리어 — 비영값 1087건
0x05ENUM수치2B열거형 (int16, big-endian). 배열 원소로 반복
0x06BOOL수치4B고정 4B int32. "TRUE"/"FALSE" 문자열이 아님
0x07FLOAT32수치4BIEEE754 단정도 (미관측, 폭은 추정)
0x08FLOAT64수치8BIEEE754 배정도 (big-endian). 가장 흔함
0x09STRING문자열가변NUL 종료 문자열. 이름·값·배열원소 모두 이 태그
0x0AARRAY컨테이너가변배열, END 로 닫힘 (원소 규칙은 ⑥)
0x0BSTRUCT컨테이너가변중첩 구조체, END 로 닫힘

🔑 헷갈리기 쉬운 셋: 0x02·0x03 은 "0 이라고 적을 때만" 쓰는 마커이고, 진짜 int8 값은 0x04 가 싣습니다. 이 구분이 배열 해석의 모호성을 통째로 없앱니다(⑥).

05

실제 바이트를 한 칸씩 — 예제 디코딩

명세 §1.4 의 실측 hex 를 디코더가 읽는 순서 그대로 짚어봅니다. 칸을 클릭하거나 다음 ▸ 로 한 스텝씩 진행하세요. 각 칸이 무슨 뜻인지 아래에 설명됩니다.

// 위 바이트를 전부 디코딩하면: { "IFEUCM_machine_configuration_struct": { "lens_magnification": 0.25, "if_sim_mode": "SIM_DISABLED", "hw_timestamp_transmission": "TRUE" } } // trailer BC 94 26 A8 → 체크섬 일치 ✓
06

디코더가 안 넘어지려면 — 까다로운 규칙 넷

여기가 진짜 핵심입니다. 순진하게 "태그 뒤엔 항상 고정폭 payload" 라고 읽으면 디싱크(정렬 어긋남)가 나서 이후 전부를 잘못 읽습니다. 실측으로 확정된 네 가지 예외를 알아야 합니다.

1

값이 0이면 payload 를 통째로 생략한다 (이름 필드)

미사용 슬롯의 nr_of_used_samples 처럼 값이 0/FALSE 일 때는 SubType 태그 바로 뒤에 다음 필드의 이름(0x09+식별자+0x00)이나 컨테이너를 닫는 END 가 곧바로 옵니다. 고정폭을 그대로 소비하면 다음 이름의 앞 글자를 삼켜 어긋납니다.

… 04 직후에 09 "next_field" 00 이 보임 ⇒ 값 0, payload 소비 안 함 ✓

판정 규칙 두 가지: (a) 다음 필드 앵커(0x09+식별자+NUL)가 바로 보이면 → 모든 스칼라에서 값 0. (b) 바로 END 가 오면 → 1바이트 폭 태그(0x01~0x04)에 한해 값 0. enum·bool·float 은 첫 바이트가 0x00 이어도 뒤에 실값이 있을 수 있어(예: float 비정규값) END 검사를 적용하지 않습니다.

2

배열의 0 은 0x02/0x03 마커로 적는다

배열 안에서 0 은 payload 없이 태그 1바이트만 씁니다. 그래서 02 02 02 02 는 "int8 값 2가 넷"이 아니라 전부 0 입니다. 이걸 모르면 02 02 를 (태그+payload)로 둘씩 짝지어 먹습니다.

position_nrs 실측 (값 캐리어는 0x04):
02 02 03 │ 04 02 04 02 04 03 04 03 04 04 …
⇒ [0, 0, 0, 2, 2, 3, 3, 4, …]  (0×3 마커 + 0x04 값 페어)

주황=마커(0x02/0x03, 값 0), 초록=0x04 값 캐리어.

3

문자열 원소는 이형(二形) — NUL 직후 바이트로 판별

배열 안 0x09 원소는 두 얼굴을 가집니다. 이름 NUL 바로 다음 바이트로 결정적으로 구분합니다.

0a 09 "TRUE" 00 09 "TRUE" 00 … 00 ⇒ ["TRUE","TRUE",…] (NUL 뒤가 0x09/그외 → bare 문자열)
0a 09 "abc" 00 0b … 00 00 ⇒ [{"abc": {…}}] (NUL 뒤가 0x0A/0x0B → 이름+컨테이너)

순진하게 읽으면 bare 문자열들을 둘씩 짝지어 {TRUE:"TRUE"} 로 오독합니다(짝수 개면 조용히 틀림). post-NUL 판별이 두 오독을 모두 차단합니다.

4

수치 배열은 값 크기에 따라 타입이 승격된다

배열은 엄격 동질이 아니라 범주 동질입니다. 값이 int8 범위(≤127)를 넘으면 같은 배열 안에서 enum(2B)으로 승격됩니다. 원소마다 자기 태그로 폭이 정해지니 섞여도 파싱은 결정적입니다.

ratios 실측 (+5 등차수열):
04 22 … 04 7c │ 05 00 81 05 00 86 …
⇒ [34, 39, …, 124, 129, 134, …]
int8(≤127) → 128 부터는 enum(2B)로 승격

단, 범주 교차(수치↔문자열↔컨테이너)는 실배열에 없습니다 → 나타나면 디싱크 신호로 취급합니다.

07

마지막 4바이트 — 트레일러 체크섬

CRC 가 아니라 base-17 곱셈 롤링 해시 입니다. 그래서 표준 체크섬 도구로는 안 잡힙니다. 본문 전체(매직 포함, 트레일러 자신은 제외)를 한 바이트씩 누적합니다.

h = 0,   각 바이트 b 마다   h = ( h × 17 + b )  mod  2³²  →  최종 h 를 big-endian 4B 로

파이썬으로

# 트레일러 직전까지 누적
h = 0
for byte in raw[:-4]:
    h = (h * 17 + byte) & 0xFFFFFFFF
assert h == int.from_bytes(raw[-4:], 'big')
✓ 실코퍼스 605/605 전수 일치 (2026-07-07)

누적이 굴러가는 모습

주의: 이 해시는 CRC 보다 오류 검출력이 약합니다(뒤 k번째의 +17 과 k+1번째의 −1 이 상쇄 가능). 무결성 확인엔 충분하지만 위변조 방지용은 아닙니다.

08

또 다른 얼굴 — 텍스트 형식

감지(②)에서 텍스트로 판정되면, 메모장으로 열리는 사람이 읽는 중첩 구조입니다. 같은 데이터를 이렇게도 표현합니다.

{
  IFXATA_STRUCT = {
    logn_id = 2,
    phys_id = 5,
    detector = [
      { name = TRUE, intensities = [1, 2, 3] },
      { name = FALSE, vals = [] }
    ],
    empty = {}
  }
}

문법 요점

member := KEY '=' value, = 앞뒤 공백 무관. 값은 struct {…} / array […] / 스칼라 중 하나. 빈 {}·[] 허용.

스칼라 변환

정수 · 실수(1.0e-3 포함) · TRUE/FALSE 불리언 · <undef>→null · "따옴표"/맨문자열.

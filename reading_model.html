.dd 재해석공리 A1 · A2

타입이 값을 담는 게 아니라
값이 태그를 고른다

기존 해석은 "태그마다 폭이 고정된 타입"이라 보고 예외를 4개 두었습니다. 렌즈를 뒤집어 수치 태그를 하나의 폭 사다리로 보면 — 인코더가 값에 맞는 최소 폭 칸을 고르는 것뿐 — 예외 넷이 규칙 둘로 녹습니다. 아래에서 직접 값을 넣어 확인해 보세요.

① 값을 넣어보기 ② 폭 사다리 (A1) ③ 렌즈 비교 ④ 예외가 녹는다 ⑤ 원소 문법 (A2)
01

먼저 직접 — 값을 넣으면 인코더가 고르는 칸

이게 공리 A1 의 전부입니다. 숫자를 입력하면 이 포맷이 그 값을 어떤 태그·몇 바이트로 기록하는지 보여줍니다. 같은 필드라도 값이 바뀌면 태그가 바뀝니다.

규칙: 정수는 들어가는 최소 폭을 고른다 — 0 은 폭0, ±127 까지 1B, ±32767 까지 2B, ±21억까지 4B, 그 밖/소수는 8B float. 다바이트는 전부 big-endian. (문자열·구조체·배열은 별도 태그 0x09/0x0B/0x0A — 사다리는 수치 전용.)

02

폭 사다리 — 수치 태그는 타입이 아니라 칸이다 (A1)

위에서 값을 바꾸면 여기 해당 칸이 켜집니다. 태그 = 그 칸의 폭. 인코더는 값이 들어가는 가장 낮은 칸을 씁니다.

"ENUM"·"BOOL"은 이름의 유물입니다. 0x06 이 담은 실측값 logical_scan_id = 129366 이 불리언일 리 없습니다 — 그냥 int32 입니다. 0x05("ENUM")가 등차수열(34, 39, …, 124, 129, 134)의 128↑ 구간을 담는 것도 열거형이 아니라 int16 이라는 증거. 이름을 int16/int32 로 바로잡으면 태그표가 깨끗한 폭 사다리가 됩니다.
03

렌즈 비교 — 같은 바이트, 두 해석

왼쪽은 기존(타입 고정) 렌즈, 오른쪽은 새 해석(값이 태그를 고른다). 바이트는 하나도 안 바뀝니다 — 보는 틀만 바뀝니다.

태그기존 렌즈 (타입 고정 + 예외)새 해석 (폭 사다리)
0x02/03 INT8_B/UINT8 — "0 전용 마커", 배열에서 특수 처리(예외 ②) int, 폭 0 — 사다리 맨 아래 칸. 특수 규칙 아님
0x04 INT8_C — 실제 int8 값 캐리어(0x02와 역할 분리 필요) int8 (1B 칸) — 0이 아닌 값이 여기부터
0x05 ENUM — 열거형(값→라벨 매핑은 포맷 밖) int16 (2B 칸) — 승격이 아니라 다음 칸일 뿐
0x06 BOOL — 불리언(4B int32로 저장…?) int32 (4B 칸) — 129366 이 불리언일 수 없음
0x08 FLOAT64 — 배정도 float64 (8B 칸) — 사다리 꼭대기(폭이 값을 못 담을 때)
— 예외 ①②④ = 서로 다른 특수 규칙 3개 전부 "최소 폭" 한 원리의 발현
04

예외가 녹는다 — 특수 규칙 → 사다리의 자연스러운 결과

"값이 태그를 고른다"를 받아들이면, 따로 외우던 예외 셋이 규칙이 아니게 됩니다. (예외 ③ 은 성격이 달라 A2 로 — §5)

②

배열의 0 마커 — 였던 것

→ 그냥 폭0 칸(0x02/0x03). 배열은 값에 맞춰 태그를 고르는 문맥이니 0 은 당연히 폭0 태그로 온다. 02 02 02 02 = 값 0 넷. "마커"라는 특별한 개념이 필요 없다.

④

수치 배열의 타입 승격 — 였던 것

→ "승격"이란 개념 자체가 불필요. 원소마다 자기 값이 자기 칸을 고를 뿐 — 124는 1B 칸, 129는 2B 칸. 배열이 "한 타입"이 아니라 원소별 최소 폭이라 폭이 섞여도 결정적이다.

①

이름 필드의 0값 payload 생략 — 였던 것

→ "0 은 폭0" 원칙의 이름-필드 발현. 측정으로 연역까지 된다: 0x04(1B 칸) 이름 필드 1087개가 전부 비영 — 0이었다면 폭0 칸으로 갔을 테니까. 즉 "생략"으로 보이던 다수가 애초에 폭0 태그였다.

한 문장: 태그를 "타입 이름"이 아니라 "이 값을 담는 데 쓴 바이트 수"로 읽으면, 예외 ①②④ 는 규칙이 아니라 "인코더는 최소 폭을 쓴다" 한 줄의 그림자였다.
05

두 번째 공리 — 배열 원소 문법 (A2)

예외 ③(0x09 원소 이형)은 폭 사다리와 무관한 문법 문제입니다. 배열 원소를 이 한 줄로 정의하면 예외가 사라집니다.

element := named_container | bare_value
named_container := 09 name 00 ( 0A array | 0B struct ) # NUL 직후가 컨테이너
bare_value := number | 09 string 00 | 0A array | 0B struct

판별은 NUL 직후 1바이트

09 "abc" 00 를 읽고, 바로 다음 바이트가 0A/0B 면 이름+컨테이너, 아니면 bare 문자열. 이게 예외 ③의 "post-NUL 판별" — 특수 규칙이 아니라 이 문법의 LL(1) 룩어헤드일 뿐입니다.

왜 결정적인가 (귀류법)

이름 원소를 bare 로 잘못 읽으면 뒤 컨테이너가 범주 위반이 되어 즉시 모순. bare 를 이름 원소로 잘못 읽으면 뒤에 컨테이너가 없어 성립 불가. 두 해석이 동시에 맞는 바이트열이 없어 1바이트 검사가 완전합니다.

✓ 이 두 공리로 재구현한 파서(dd_unified.py) — 실측 패턴 15종 통과 · 생성 코퍼스 수천 파일서 기존 파서와 동치

정리: A1 값이 태그(폭)를 고른다 + A2 element := named_container | bare_value. 이 둘이면 예외 4개가 다 설명됩니다. 남은 미결은 폭이 아니라 부호(int16 vs uint16 — 음수·경계값 미관측)와 0x01 의 정체뿐.

.dd Binary TLV · Byte Layout

바이트 구조 한눈에

칸 하나 = 바이트 하나. 색은 역할입니다. 파일 전체 → 필드 하나 → 값의 폭 → 중첩 → 배열, 그리고 파서가 넘어지는 예외 4가지까지.

매직/트레일러 틀 Type(0x09) 이름 SubType/수치 값 컨테이너 END(0x00) 흐린 칸 = 앞뒤 문맥 점선 프레임 = 특이 지점

04

중첩 — 여는 태그와 END 는 짝

STRUCT/ARRAY 는 값 자리에 자식들을 담고 END(0x00)로 닫습니다. 들여쓰기가 곧 깊이입니다.

0B┐ 최상위 STRUCT 열기
09"outer_struct" 000B┐ 필드 값이 또 STRUCT → 한 단계 더
09"ratio" 00083F D0 00 00 00 00 00 00스칼라 필드
09"mode" 0009"SIM_DISABLED" 00문자열 필드
00┘ 안쪽 STRUCT 닫기
00┘ 최상위 STRUCT 닫기

SubType 자리의 0x09 는 "값이 문자열" 이라는 뜻 — 필드 시작의 0x09 와 같은 바이트지만 위치가 역할을 정합니다.

해결 알고리즘 — 정규식 앵커 룩어헤드dd_main.py
# "다음 필드 이름" 패턴을 정규식으로 정의 — 소비 없이 미리보기(lookahead)만 한다
KEY_ANCHOR = re.compile(rb'\x09([A-Za-z_][A-Za-z0-9_.\-]{0,63})\x00')

def read_scalar(subtype):
    if KEY_ANCHOR.match(raw, i):      # ① 커서 위치가 곧바로 "09+식별자+00" 이면
        return 0                       #    → payload 생략된 것. 소비 0바이트, 값 0
    if size == 1 and raw[i] == 0x00:  # ② 1바이트 태그 + 바로 END → 마지막 멤버의 0
        return 0                       #    (0x00을 값으로 읽어도 어차피 0이라 안전)
    v = unpack(fmt, raw[i:i+size]); i += size  # ③ 아니면 정상 고정폭 소비
    return v
왜 이 정규식이 결정적인가: 앵커를 아무 0x09 가 아니라 「0x09 + ASCII 식별자(첫 글자 영문/_, 최대 64자) + 0x00」 전체 패턴으로 제한했기 때문입니다. float64 payload 안에 우연히 0x09 바이트가 나와도 뒤가 식별자+NUL 형태가 아니면 매치되지 않아 "도미노 오정렬"이 안 생깁니다. ②를 1B 태그로 한정한 이유: enum(2B)/bool·float(4~8B)은 첫 바이트가 00 이어도 나머지 바이트에 실값이 있을 수 있어(float 비정규값 등) 잘라먹으면 안 됩니다.

SCALAR_FMT = { 0x04: ('>b', 1), 0x05: ('>h', 2), 0x06: ('>i', 4), 0x08: ('>d', 8), … }

while raw[i] != END:
    t = raw[i]; i += 1
    fmt, size = SCALAR_FMT[t]        # 원소마다 "자기 태그"로 폭을 새로 결정
    arr.append(unpack(fmt, raw[i:i+size])); i += size

    # 범주 불변식: 첫 원소의 범주(수치/문자열/컨테이너)를 dom 에 기록,
    # 이후 원소가 범주를 벗어나면 → 값이 아니라 파싱 디싱크로 판정
    dom = dom or category(t)
    assert category(t) == dom
핵심 아이디어: "배열 = 한 타입" 가정을 버리고 폭 결정을 원소 단위로 국소화하면, int8→enum 승격이 배열 중간에 일어나도 각 원소가 자기 폭만큼만 정확히 소비하므로 파싱이 결정적입니다. 대신 실코퍼스에서 관측된 더 약한 불변식(범주 동질성)을 검사로 남겨서, 진짜 어긋남(수치 배열에 문자열/컨테이너 태그 등장)은 놓치지 않고 잡아냅니다.

이 규칙들이 맞다는 건 어떻게 증명했나

위 네 해법은 각각의 지점을 고치지만, "규칙 전체가 파일 전체를 유일하게 설명하는가"는 별도 알고리즘으로 검증했습니다.

elif len(solutions) == 0: status = 'failed'    # 구조 오류 — 실패 지점 hexdump 진단
else:                    status = 'ambiguous'  # 모호 — 두 해가 갈라지는 첫 지점 diff 출력
결과: 실코퍼스 605개 전부 unique(유일해) — 모호 0건, 오류 0건. 즉 위 규칙 집합은 코퍼스의 모든 바이트를 단 한 가지 방법으로만 설명합니다. 휴리스틱 단일-pass 파서 (dd_main.py)와 결과도 100% 일치. 규칙이 하나라도 틀리면(예: 0x02 가 비영값을 싣는 반례 등장) 이 검증기가 즉시 '모호' 또는 '불일치'로 잡아냅니다.
08

근본 해법 — 예외 4개는 공리 2개였다

예외들은 하드코딩이 아니라 잘못된 렌즈의 그림자였습니다. "태그마다 폭이 고정이고 필드는 스키마 타입을 쓴다"고 보면 예외 4개가 필요하지만, 렌즈를 바꾸면 전부 사라집니다. (dd_unified.py 로 구현, dd_prove.py 로 실행 증명)

공리 A1 — 값이 태그를 고른다 (최소 폭 인코딩)

수치 태그는 타입이 아니라 폭 사다리다: 0x02/0x03=0B(값 0) → 0x04=1B → 0x05=2B(int16) → 0x06=4B(int32) → 0x08=8B. 인코더는 값이 들어가는 최소 폭을 고른다. "ENUM"·"BOOL" 이라는 이름은 유물 — logical_scan_id=129366 이 "BOOL"일 리 없다.

공리 A2 — 원소 문법

element := named_container | bare_value. 배열 원소 0x09 는 NUL 직후 1바이트가 0A/0B 면 이름+컨테이너. post-NUL 판별(예외 ③)은 이 문법의 LL(1) 룩어헤드일 뿐이다.

적대 검증에서 실제로 깨진 것과 살아남은 것

독립 에이전트 4개가 반박을 시도했고, 2건이 정당하게 깨져서 수정됐습니다:

깨짐 ① — "동치는 규칙이 허용하는 인코딩 전체에서 성립" 은 과대주장. 스펙 표는 0x02/0x03 을 "0~1B"로 헷지해 두었기에, 규칙상 가능하지만 인코더가 절대 안 만드는 02 05(0x02+비영 payload) 같은 바이트에서 dd_main({a:5})과 공리 파서({a:0})가 갈립니다. 더 중요한 발견: 이 파일을 dd_strict 는 경고 없이 '유일해'로 통과시킵니다 — 스펙 §4 의 "반례가 나타나면 즉시 검출" 주장에 구멍. → 공리 파서에 anomalies 검출을 추가해 실질 트립와이어로 만들었습니다 (동치 주장은 "인코더 이미지 위에서"로 정정).

깨짐 ② — 초기 열거기에 dd_strict 에 실재하지 않는 "배열 1B 생략" 유령 분기가 있어 유효 파일 698개 중 59개의 모호성을 과대집계했습니다 (dd_strict 의 해당 코드는 호출되지 않는 죽은 코드임을 에이전트가 규명). → 제거 + dom 동질성 모델링 추가 → 판정 정합 698/698.

살아남음 — P2(pure 룰 해 ≤1)는 3,431개 변형 퍼즈와 코드 검토 모두에서 생존: pure 문법은 모든 위치에서 대안이 최대 1개라 구성적으로 무모호합니다. 공리 감사(V3)도 연역의 뼈대를 건전 판정 — 단 아래 '남은 미결'이 정밀해졌습니다.

확정까지 남은 측정 1회: 실코퍼스에서 python dd_prove.py measure dumps/ — 카운터 [1]~[5] 가 전부 0 이면 코퍼스는 pure 이미지 안이고 생략 룩어헤드가 전혀 없는 결정적 파서로 충분합니다. 남은 미결(적대 검증으로 정밀화): ⑴ 0x06 제로 1건·0x08 제로 352건이 explicit payload 인지 생략인지, ⑵ 0x02/0x03 제로 652건이 폭0인지 explicit 00 payload 인지 (measure 카운터 [4][5]), ⑶ 0x05/0x06 의 부호(int16 vs uint16)와 승격 경계(32767 vs 65535) — 음수·경계 값 미관측, ⑷ 0x01 의 정체. 그리고 스펙 문서 자체의 내부 모순 한 건: §1.3 "0x06 1개(0)" vs §4 "logical_scan_id=129366(비영)" — 매직 없는 변형 파일이 측정에서 제외된 스코프 문제로 추정.
